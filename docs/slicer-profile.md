# Slicing like their prints: the contract

`design/getting-started/` ("Slicing like their own prints", picked 5 October 2026). On a printer someone else set up,
Elyir Bench slices with the profile their own prints already carry: every file OrcaSlicer writes ends with its whole
profile, resolved (`; CONFIG_BLOCK_START` … `; CONFIG_BLOCK_END`, about 630 settings). That is what
`slicer/export_presets.py` freezes by hand on a desktop today. This file is the contract between the printer's side
(the Moonraker component, a pure reader module, the slicer) and the app.

## Where it happens

On the printer, in the Moonraker component: it can read its own gcodes folder. What it learns goes where the slicer
already looks, so slicing anywhere (on this printer, or on another printer that lends its slicer) uses it unchanged:

```
printer_data/config/elyir-bench-slicer/
  printer.json              {"machine", "process", "plate", "tools", "materials": {...}, "learned": {...}}
  presets/0-learned/        one Orca preset per file: the machine, the process, one per material
```

A `printer.json` without `"learned"` was written by hand (the owner's printers): it is never touched, and the profile
state says `yours`.

## The reader (`printer/orca_profile.py`, standard library only, pure)

- **read(path)**: the settings block from the last ~256 KB of a file, as `{key: raw text}`, and the generator from its
  first lines (`; generated by OrcaSlicer 2.3.1 on …`). Files without a block (Cura, PrusaSlicer for now) give nothing.
- **ours(block)**: a file Elyir Bench sliced itself is skipped, so it never learns from itself. The slicer writes a
  marker line for that (`; sliced by Elyir Bench`, near the top; slicer/elyir_bench_slice.py).
- **presets(block)**: the block as three flat Orca presets, `machine`, `process`, `filament`, each named from the
  block's own `printer_settings_id`, `print_settings_id`, `filament_settings_id`. Which key goes where, and whether a
  value is a list, comes from `slicer/orca_keys.json`, generated once from OrcaSlicer's own bundled profiles by
  `scripts/orca-keys.py` (committed; regenerate when the pinned Orca moves). Values are read the way Orca writes them:
  lists of numbers or points comma-separated (`0.4,0.4`, `0x0,350x0`), lists of text quoted and semicolon-separated
  (`"a";"b"`), single text with `\n` for new lines, quoted when Orca quoted it.
- **group(files)**: files with the same machine, process, nozzle and bed shape are one profile: how many files, the
  newest, which Orca versions, and per material (`filament_type`) the newest file's filament preset.
- **checks(profile, klipper)**: the bed against Klipper's limits (`toolhead.axis_maximum`, within 2 mm), and the first
  word of `machine_start_gcode` against the commands Klipper has (its `gcode_macro` objects, plus `G28` and the like).

**Fidelity:** presets rebuilt from a file's block must match what `export_presets.py` froze from the same presets on
the desktop, key for key, apart from keys the block doesn't carry (names, `inherits`, `from`, version stamps).
Checked against Workshop: its `presets/0-resolved/` and its files sliced by the desktop's OrcaSlicer 2.3.1.

## What the component says (`GET /printer/intent/profile`)

```jsonc
{
  "state": "using",            // using | ask | none | yours | newer
  "told": false,               // the app showed "Slicing like your prints" once (profile_told)
  "using": "a1b2",             // the id in `found` it slices with, or null
  "found": [
    { "id": "a1b2", "printer": "Voron 2.4 350", "process": "0.20mm Standard @Voron", "nozzle": 0.4,
      "bed": [350, 350], "files": 15, "slicer": "OrcaSlicer 2.3", "newest": 1791230000,
      "materials": { "PLA": { "preset": "Generic PLA @Voron", "files": 12 }, "PETG": { "preset": "…", "files": 3 } },
      "start": "PRINT_START",
      "checks": { "bed_ok": true, "bed_klipper": [350, 350], "start_ok": true } }
  ],
  "bed_klipper": [350, 350]     // for the no-files path, and to say a mismatch in words
}
```

- `using` (auto): no hand-made printer.json, and the recent files agree (one profile, or one holds at least 80% of
  the last 20 files). The component writes printer.json and the presets by itself. `told` stays false until the app
  has shown the sheet once.
- `ask`: the files disagree (two nozzles, two processes): the app asks once, showing how many files used each.
- `none`: no file carries a block. Slicing waits (the app says to slice one file in OrcaSlicer and print it).
  Picking from Orca's own list by bed size is phase 2.
- `newer`: files newer than the profile in use carry a different one: a one-line offer on Print, never a switch.
- `yours`: printer.json was written by hand; nothing is learned.
- A profile whose `checks` fail is never used by itself: it shows, with the mismatch said in words.

The scan runs at start and when the gcodes folder changes (Moonraker's file events), not on every request.

## Purposes on a learned profile

Decided 5 October 2026: on a printer whose printer.json was learned, **Everyday is exactly their own settings**,
and the spool's tweaks (the PETG changes in `MATERIALS`) stay off, since their files already carry their own filament
choices. The other purposes (Quick draft, Looks best, Strong, …) still adjust from their settings. A hand-made
printer.json works as before. `slicer/elyir_bench_slice.py` `plan()`, `Printer.learned`.

## Actions (`POST /printer/intent/action`)

| action | does |
|---|---|
| `profile_use` `{id}` | writes printer.json and presets/0-learned/ from that profile; `using` = it |
| `profile_told` | the "Slicing like your prints" sheet was shown |
| `profile_keep` | the `newer` offer is declined; it isn't offered again for that profile |

## The app

- **First slice** (Print › Print a model, `state` using and not `told`): the sheet "Slicing like your prints": found in
  N of your files, made with OrcaSlicer X; printer, settings, materials (from your files; the rest: Orca's own for this
  printer), starts with their own macro. **Pick a model** sends `profile_told` and goes on; **Other settings in your
  files (n)** lists the others to choose from.
- **ask**: the same list before the first slice, each with its file count; tapping one sends `profile_use`.
- **newer**: a one-line card on Print: "Your newer prints use X. Slice like those from now on?" Use them / Keep.
- **none**: Print a model says "Slice one file in OrcaSlicer and print it, and Elyir Bench learns your settings from it."
- Words as in the boards (`c-slice-found`, `c-slice-pick`, `c-slice-newer`), "Elyir Bench" for the product name.

The simulator serves `/printer/intent/profile` and the actions, with scenarios `profile_found`, `profile_ask`,
`profile_newer` and `profile_none`.

## As built on the printer's side (5 October 2026)

Branch `sp-api`. What differs from the contract above, and why:

- **`orca_keys.json` comes from Orca's own source, not only its bundled profiles.** About 45 settings Orca writes
  into every file are set by no bundled preset (`top_surface_density`, `skin_infill_depth`...), and vendors write
  some lists as single values (`z_hop_types` single in 44 presets, a list in 130). `scripts/orca-keys.py` reads
  Orca's `Preset.cpp` (which keys a print, filament and printer preset hold) and `PrintConfig.cpp` (each key's
  type) at each version, fetched from GitHub by tag, and checks them against the bundled profiles. It covers the
  desktop's 2.3.1 and the printers' pinned 2.4.2 (2.4 added about a hundred settings), the newer winning; two keys
  became lists in 2.4.2 (`nozzle_type`, `nozzle_volume`), so files from 2.3 read them as single (`lists_since`).
  No setting is in two kinds; only `compatible_printers` and the like are, which are never learned. The JSON also
  says which lists are text (`strings`), which machine keys are per nozzle (`extruder`) and which filament
  overrides a file leaves out when they're unset (`nil`).
- **`read(path)` gives more than the block:** `{path, modified, block, slicer, ours, used}`. The marker is near the
  top of the file, not in the block, so **`ours(f)` takes what `read()` gives**. `used` is which filaments a file
  printed with (from `; filament used [mm]`): a file from a printer with a unit carries every slot's filament, and
  only the ones it printed with count as its materials.
- **`presets(block, keys, tool, version)`**: `tool` picks one filament of several, `version` is the Orca that wrote
  the file. Orca writes the filament colours into `extruder_colour`, so it's cut to one per nozzle (its value is
  the filament's colour, not the machine preset's). Filament overrides Orca leaves out when unset come back as
  `["nil"]`, as Orca keeps them.
- **`agreed(profiles, files)`** and **`answer(...)`** hold the rule for `using` / `ask` / `newer` in the pure module,
  so it's tested without Moonraker; **`learned(profile)`** and **`printer_json(profile)`** say what to write.
- **The answer has `newer`** (the id offered, or null) besides the contract's fields, and each `found` entry also
  has `machine` (the preset name), `plate` and `slicers` (every Orca version seen). `newer` is only offered for
  files newer than the profile in use *and* than the moment it was picked, so picking an older profile from `ask`
  doesn't offer the newer one straight back. `profile_keep` takes an optional `{id}` (default: the one offered).
- **`learned.from_files`** is the list of files (relative to gcodes) the presets came from, not a count.
- **A printer.json that can't be read** (someone editing it in Mainsail) counts as `yours`: never written over.
- **Checks unknown** (Klipper not ready) are `null`, and a profile is only used by itself when both are `true`.
- **`0-learned` vs `0-resolved`:** the slicer loads preset folders in sorted order and the first name wins, so
  `0-learned` (l before r) beats `0-resolved` and the person's own folders. That's on purpose: a learned
  printer.json references the learned names, and a printer with a hand-made printer.json never gets a 0-learned.
  `profile_use` replaces the whole folder, so a profile used before leaves nothing behind.
- **`tools`**: 1, or every slot the intent layer counts on the printer's filament units. **`start_macro`**: true
  when Klipper has `ELYIR_BENCH_PRINT_START` (the start macro is included) or the printer.json before said so.
- **The slicer reads printer.json itself.** Before, the installer copied printer.json into the service's config at
  each apply, and without one the service didn't run. Now the config names the printer's folder (`home`) and the
  service reads printer.json and the presets when they appear and whenever they change (every 5 s at most), so a
  learned profile slices from the next request. Until then `/slice/options` answers 404 `{error, settings: false}`
  ("Slice one file in OrcaSlicer and print it, and Elyir Bench learns them from it."); the installer's health check
  only asks once printer.json is there.

**Fidelity, checked against Workshop** (its frozen `0-resolved` presets and its files, copied read-only; numbers from
`printer/orca_profile.py` against them, by `presets()` key by key):

- A control file sliced on the Mac by Orca 2.3.1 from Workshop's frozen presets: process 107 of 107 keys the same,
  filament 94 of 94 (with the unset overrides as nil), machine 55 of 58. The three: `z_hop_types` is a list in
  Orca (`coEnums`; Orca's own 3MF says so) but a single string in the frozen preset, because export_presets copies
  the Voron vendor file's spelling (Orca reads both); `extruder_colour` (Orca writes the filament colour there);
  `min_layer_height` `0.10` frozen against `0.1` from the file (the same number).
- The desktop's own files from December 2025 (Body80, rear_body, cable_chain, front_bearing_holder, Body2; 8
  filaments, printed with slot 6): every filament in them whose preset is frozen matches 94 of 94. The process
  differs in exactly the 8 keys the file's own `different_settings_to_system` lists (bottom and top shells, skirt,
  infill and pattern, supports): changes made in Orca for those prints, which is what slicing like their prints
  should keep. The machine differed in `machine_max_jerk_x/y` (12 in the files, 9 frozen) and the process in
  `min_skirt_length` (0 against 4): **a bug in `Presets`**, fixed on this branch: a parent like
  `fdm_klipper_common` is in many vendors' folders and Custom's won; Orca uses the child's own vendor. Workshop's
  `0-resolved` was frozen with it, so **re-export it** (`export_presets.py`, as in docs/slicer.md): only those three
  keys change, to what the desktop really prints with.
- Round trip: presets learned from Body80 and rear_body, sliced again by Orca 2.3.1 on the Mac: 502 of 504 settings
  in the new file's block are the same as in the original; the other two are `extruder_colour` and `thumbnails`
  (`48x48/PNG,300x300/PNG` written back as `48x48/PNG, 300x300/PNG`).
- What a block holds: 528 settings in a 2.3.1 file, 504 of them in a preset; 625 in a 2.4.2 file, 592 in a preset.
  The rest are names and the project's own (below).
- Keys a block doesn't carry: names (`inherits`, `from`, `setting_id`, `version`, `instantiation`,
  `compatible_*`, `print_host`...), legacy keys Orca 2.3 dropped (`adaptive_layer_height`, `wall_infill_order`,
  `tree_support_with_infill`), and unset filament overrides (filled in as nil). Project-level keys in the block
  that belong to no preset are left out: `curr_bed_type` (it goes to printer.json's `plate`), `filament_colour`,
  `filament_ids`, `flush_volumes_*`, `wipe_tower_x/y`, `different_settings_to_system`, `inherits_group`, and in 2.4
  `filament_map`, `extruder_ams_count`, `nozzle_volume_type`.
- Files the Pi's Orca 2.4.2 sliced (Elyir Bench's own, from before the marker) carry about a hundred more keys, every
  one that belongs to a preset known to orca_keys.json; their values differ from the frozen presets only where Elyir Bench's purposes, PETG
  settings and the pressure-advance test changed them. Not checked: Orca 2.4.2 slicing from learned presets (it
  isn't on the Mac), and a 2.4 desktop's files.

Still needs a real stranger's printer: files from another slicer setup (another vendor's presets, a printer with
more than one nozzle, a hand-edited start G-code with templates before the first command), a gcodes folder with
hundreds of files and subfolders, `newer` across a real week of prints, the start-macro flag with their own
`PRINT_START`, and Orca 2.4.2 on the printer slicing from a 2.3 desktop's learned presets.

## As built in the app

`app/src/intent/profile.ts` (pure, pinned by `app/tests/profile.test.ts`), drawn by `app/src/components/profile/`
(`FoundSheet.vue`, `ProfilesSheet.vue`, `NewerCard.vue`) on `PrintScreen.vue`; the simulator's side is
`simulator/slicer_profile.py`. Where it differs from the text above, or fills a gap in it:

- **Which profile is "newer"**: the contract has no field for it, so the app takes the profile in `found` with the
  latest `newest` that is newer than the one in `using`, and sends its id with `profile_use`.
- **"Keep Standard"**, as on c-slice-newer, not plain "Keep": the profile in use, named by what differs: the process's
  short name (`0.20mm Standard @Voron` → Standard), else its nozzle (`Keep 0.4 mm`), else its printer. When only the
  nozzle differs, the line says "Your newer prints use a 0.6 mm nozzle."
- **Picking from the list** (ask, or Other settings): `profile_use`, then the found sheet again for the chosen profile
  (state `using`, not told), so Pick a model there sends `profile_told` and opens the file picker in the same tap (a
  browser only opens it from one). In the ask state that is one more sheet than the contract's text suggests.
- **The list's words** (no board; c-slice-pick is phase 2): ask is titled "How do you slice for Voron?", "Your files
  were sliced two ways. Elyir Bench slices like the one you pick."; from the found sheet, "Settings in your files", with
  a back link to it and the one in use ticked. Each row: the process, then the printer when they differ (Orca's
  "0.6 nozzle" suffix left off), the nozzle and the file count.
- **Materials line**: "the rest" are the materials loaded on the printer (`intent.spools`) that no file carries:
  "From your files. ASA: Orca's own for this printer.", or "Others: …" when everything loaded is covered.
- **Failed checks** are said on the sheet and in the list, in amber: "Made for a 300 × 300 bed; Klipper says this one
  is 350 × 350.", "Starts with PRINT_START, which Klipper here doesn't have." The sheet then leaves out "Nothing to set
  up." A profile that fails can still be picked by hand.
- **Print a model's subtitle** ends "Sliced like your prints." (instead of "I'll set it up for Voron.") while `state`
  is `using` or `newer`, after c-slice-newer's card.
- **Where**: phones and computers at home only, where Print a model shows; the panel and away are unchanged. The
  profile is asked when Print opens (and on reconnecting), and again after each action; a printer that doesn't answer
  `printer.intent.profile` slices as before.
- **Simulator**: every scenario but the four `profile_*` ones answers `yours`. Those four give the one spool ASA on a
  printer without a unit (`--no-ace`), so the materials line reads as on the board.
